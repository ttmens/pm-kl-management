# 产品简报：产品知识平台（KL Management）

## 一句话描述
面向企业 AI 编程场景的「产品知识平台」，将业务知识（biz_kl）与系统逻辑知识（sys_kl）结构化沉淀，供 Agent/IDE 消费，解决「懂业务 + 懂系统」的上下文碎片化问题。

## 背景
企业 AI 编程强依赖内部业务知识。以供应链 IT 为例：需在百万行级存量系统上做功能维护与演进，必须先把「产品知识」结构化沉淀，再供 Agent/IDE 消费。

知识分两层：
- **biz_kl（业务知识库）**：以产品历史设计文档、PRD、运维/变更记录为输入，压缩抽象为可检索的业务语义（领域概念、流程、规则、边界）。
- **sys_kl（系统逻辑知识库）**：以代码为基准，按 DDD 分层（领域/应用/基础设施等）叠加专家标注，逆向沉淀模块职责、调用链、扩展点、与 biz_kl 的映射。

## 要解决的问题
团队目前知识分散在文档、代码、人口述中，AI 编程时上下文碎片化，无法稳定支撑「懂业务 + 懂系统」的协同维护。

## 目标用户
1. **领域专家 / 老产品**：贡献与审核 biz_kl、sys_kl
2. **开发 / AI 编程使用者**：在编码、评审、排障时消费知识
3. **平台管理员**：权限、版本、质量与治理

## 核心能力（产品范围）
1. **知识构建**：多人协作录入/导入/逆向草稿 + 审核发布
2. **知识应用**：对接 AI 编程（上下文注入、问答、变更影响分析）
3. **知识管理**：版本、权限、血缘、过期与冲突处理

## MVP 范围
- 单产品、单仓库试点（供应链 IT 子系统 1 个 bounded context）
- biz_kl：支持文档导入 + 结构化条目（概念/流程/规则）+ 简单检索
- sys_kl：支持按 DDD 模块手工/半自动挂载代码路径 + 专家注释（不要求首轮全自动百万行逆向）
- 应用：提供「给 Agent 用的知识包」导出或 API（先只读）
- 管理：草稿/已发布、负责人、基础审计日志

## 成功指标（MVP）
1. 一个试点 BC 内，biz_kl + sys_kl 各 ≥20 条可发布条目，且可互链（业务概念 ↔ 代码模块）
2. 给定 1 个真实维护场景（小功能变更），Agent 仅消费本平台知识即可完成方案草稿（人工验收通过率 ≥70%）
3. 3 角色（专家/开发/管理员）协作流程跑通，无人口述补全关键上下文

## 约束
- 产物与界面文案：简体中文
- 架构思路：DDD；知识模型需区分 biz_kl / sys_kl，禁止混库
- 首期不做：全仓自动静态分析引擎、多租户 SaaS 计费、替换现有 Git/文档系统

## 非目标
- 不做通用企业搜索/大杂烩 RAG
- 不做全自动百万行代码逆向（首期允许人工+模板+半自动）
- 不做完整 IDE 插件市场（先 API/导出）

## 开放假设（Open Assumptions）
1. **供应链 IT 团队愿意配合试点**（confidence: high）—— 需要至少 1 名领域专家 + 2 名开发承诺在 MVP 周期内贡献 biz_kl / sys_kl 条目并参与验收。
2. **现有代码仓库可被安全访问用于静态分析**（confidence: medium）—— sys_kl 半自动挂载需要读取代码结构；若仓库权限或合规流程阻碍，首轮可能需要手动截图/导出替代。
3. **Agent 消费端已有基础上下文注入能力**（confidence: medium）—— 成功指标 #2 假设 Agent 端能够接收并解析本平台导出的「知识包」；若 Agent 侧尚未就绪，MVP 验收需要改为人工模拟消费。
4. **DDD 分层映射可由现有架构师/老员工提供**（confidence: high）—— sys_kl 的 DDD 模块划分依赖领域知识，假设团队内有熟悉 DDD 的架构师可参与标注。
5. **首期试点范围控制在单个 bounded context**（confidence: high）—— 避免 MVP 阶段跨多个 BC 导致知识模型复杂度爆炸；后续迭代再扩展。

# 上下文：产品知识平台（KL Management）

## Glossary（术语表）

| 术语 | 英文 | 说明 |
|------|------|------|
| **biz_kl** | Business Knowledge Library | 业务知识库，以产品历史设计文档、PRD、运维/变更记录为输入，压缩抽象为可检索的业务语义（领域概念、流程、规则、边界）。 |
| **sys_kl** | System Knowledge Library | 系统逻辑知识库，以代码为基准，按 DDD 分层叠加专家标注，逆向沉淀模块职责、调用链、扩展点，以及与 biz_kl 的映射关系。 |
| **BC** | Bounded Context | 领域驱动设计中的有界上下文，界定一个模型的适用边界；MVP 试点限定在单个 BC 内。 |
| **DDD** | Domain-Driven Design | 领域驱动设计方法论，用于指导 sys_kl 的分层结构（领域层、应用层、基础设施层）与业务模型的映射。 |
| **知识包** | Knowledge Package | 平台输出的结构化知识单元，供 Agent/IDE 消费，包含 biz_kl 条目、sys_kl 条目及两者间的互链关系；MVP 阶段支持只读导出或 API 拉取。 |
| **血缘** | Lineage | 知识条目的来源追踪与版本关联，记录条目由谁创建/修改、依据什么原始文档或代码片段生成，用于审计与冲突解决。 |

## 领域上下文

### 用户角色与职责
- **领域专家 / 老产品**：拥有业务上下文深度，负责 biz_kl 条目的贡献、审核与业务语义校准。
- **开发 / AI 编程使用者**：在编码、评审、排障场景中消费知识，是平台的最终用户与价值验证者。
- **平台管理员**：负责权限管理、版本治理、质量审核与审计日志，保障平台运行的秩序与合规。

### 关键业务流程
1. **知识构建**：录入/导入 → 草稿 → 审核 → 发布（多人协作）
2. **知识应用**：Agent 请求知识包 → 平台返回结构化上下文 → Agent 消费生成方案
3. **知识管理**：版本控制、权限分配、血缘追踪、过期与冲突处理

### 技术约束
- 产物与界面文案使用简体中文
- 知识模型严格区分 biz_kl / sys_kl，禁止混库
- 架构采用 DDD 思路，sys_kl 按 DDD 分层组织

# 决策日志（Architecture Decision Records）

## ADR-001: biz_kl 与 sys_kl 严格分离，禁止混库

**状态**: Accepted  
**决策日期**: 2026-06-07  
**决策者**: pm-aligner（基于简报约束推导）

### 背景
平台需要同时管理业务知识（biz_kl）和系统逻辑知识（sys_kl），两者来源、生命周期、消费场景均不同。简报明确要求"知识模型需区分 biz_kl / sys_kl，禁止混库"。

### 决策
biz_kl 与 sys_kl 采用独立存储与独立数据模型，仅通过互链关系（业务概念 ↔ 代码模块）建立关联。

### 理由
- 业务知识变更频率低、依赖专家审核；系统知识变更频率高、随代码迭代
- 两者的检索模式不同：biz_kl 偏语义检索，sys_kl 偏结构化查询
- 分离便于权限控制（专家管 biz_kl，开发管 sys_kl）
- 降低 MVP 阶段的模型复杂度

### 后果
- ✅ 模型清晰，便于分角色治理
- ⚠️ 需要维护跨库的互链关系，增加一致性校验成本
- ⚠️ 跨库联合查询需要额外设计（如知识包组装时的拼接逻辑）

---

## ADR-002: MVP 阶段 sys_kl 采用半自动挂载，不追求全自动逆向

**状态**: Accepted  
**决策日期**: 2026-06-07  
**决策者**: pm-aligner（基于简报约束推导）

### 背景
供应链 IT 系统为百万行级存量代码，全自动静态分析引擎建设成本高、周期长。简报明确"首期不做全仓自动静态分析引擎"，但允许"人工+模板+半自动"。

### 决策
MVP 阶段 sys_kl 条目通过以下方式生成：
1. 专家手工标注核心模块
2. 半自动工具辅助提取模块结构（如 AST 解析、调用链提取）
3. 模板化批量导入辅助数据

### 理由
- 百万行代码全自动逆向工程投入产出比低
- 核心模块（高频变更、高业务价值）优先覆盖即可验证价值
- 半自动方式可快速迭代，积累标注数据后反哺自动化引擎

### 后果
- ✅ 大幅降低 MVP 开发成本，缩短验证周期
- ⚠️ 需要领域专家投入时间进行手工标注
- ⚠️ 覆盖率有限，初期可能遗漏边缘模块

---

## ADR-003: MVP 阶段知识消费仅提供只读 API/导出，不建设 IDE 插件

**状态**: Accepted  
**决策日期**: 2026-06-07  
**决策者**: pm-aligner（基于简报约束推导）

### 背景
简报明确"不做完整 IDE 插件市场（先 API/导出）"，MVP 范围中知识应用定位为"给 Agent 用的知识包导出或 API（先只读）"。

### 决策
MVP 阶段知识消费接口：
1. RESTful API：Agent 可拉取知识包（JSON 格式）
2. 文件导出：支持 JSON/Markdown 格式离线使用
3. 仅支持只读操作，不开放写入或交互式编辑

### 理由
- IDE 插件开发涉及多编辑器兼容、UI/UX 设计，投入大
- Agent 消费是核心验证场景，API 接口更直接
- 只读设计降低安全与权限复杂度

### 后果
- ✅ 聚焦核心价值验证，避免 IDE 兼容性泥潭
- ⚠️ 开发者体验不如原生 IDE 插件流畅
- ⚠️ 需要 Agent 侧具备 API 消费能力（见 Assumption #3）

---

## ADR-004: MVP 技术栈选择——轻量 Web 应用（FastAPI + SQLite + 静态前端）

**状态**: Proposed  
**决策日期**: 2026-06-07  
**决策者**: pm-analyst

### 背景

MVP 需要快速验证 biz_kl/sys_kl 双库 + 知识包导出的核心价值，技术栈需满足：开发速度快、部署简单、后续可迁移。

### 决策

- 后端：Python FastAPI（RESTful API，原生异步，类型安全）
- 存储：SQLite（单文件数据库，MVP 足够，后续可迁移 PostgreSQL）
- 前端：静态 HTML + HTMX（无需构建工具，服务端渲染）
- 部署：单机 Python 进程，无容器依赖

### 理由

- 团队有 Python 经验，FastAPI 学习成本低
- SQLite 零配置，适合单 BC 试点（数据量 ≤1000 条目）
- 静态前端 + HTMX 避免前端工程化开销
- 技术栈轻量，验证失败时沉没成本低

### 后果

- ✅ 2-4 周可完成 MVP 开发
- ✅ 部署极简，一台机器即可运行
- ⚠️ SQLite 不支持高并发，但 MVP 阶段用户 ≤10 人
- ⚠️ 后续扩展需迁移数据库，但数据结构设计时可预留兼容性

---

## ADR-005: 知识包导出格式——JSON Schema + Markdown 双格式

**状态**: Proposed  
**决策日期**: 2026-06-07  
**决策者**: pm-analyst

### 背景

MVP 需要提供「给 Agent 用的知识包」，消费端可能是 API 调用也可能是离线文件。

### 决策

- JSON 格式：结构化数据，包含 biz_kl 条目、sys_kl 条目、互链关系、血缘信息，符合预定义 JSON Schema
- Markdown 格式：人类可读版本，按业务概念分组，每条包含概念描述、关联代码模块、变更历史

### 理由

- JSON 适合 Agent/API 消费，可被程序解析
- Markdown 适合人工审阅和 Git 版本控制
- 双格式覆盖 MVP 两种消费场景（API 拉取 + 文件导出）

### 后果

- ✅ 同时满足机器和人类消费
- ⚠️ 需维护两种格式的一致性（可由同一数据源生成）
- ⚠️ JSON Schema 需要版本管理，向后兼容

# 01 — 调研报告：企业 AI 编程场景下的产品知识平台

**项目：** pm-kl-management  
**阶段：** 调研（第 2 阶段）  
**日期：** 2026-06-07  

---

## 1. 执行摘要

本报告调研 **企业内部知识管理平台**、**代码知识库工具**、**DDD 知识建模实践** 与 **AI 编程上下文注入** 四类方向，为「biz_kl + sys_kl 双层知识平台」定位提供依据。

**关键发现：** 通用 KM 平台（Confluence、Notion、Glean）擅长文档沉淀与检索，但**不区分业务知识与系统逻辑知识**；代码智能工具（Sourcegraph Cody、GitHub Copilot）擅长代码理解，但**缺少业务语义层**。将 biz_kl / sys_kl 分离并通过「知识包」结构化导出给 Agent/IDE，是当前竞品尚未覆盖的差异化空间。

---

## 2. 竞品对比表（企业知识管理 + AI）

| 竞品 | 类别 | 核心能力 | 定价（约） | 优势 | 劣势 | 置信度 |
|---|---|---|---|---|---|---|
| **Confluence + Rovo** | 企业 Wiki + AI | 文档协作、跨应用搜索、AI 起草与摘要 | 标准 ~$5.75/人/月 | Atlassian 生态深、研发友好 | 重、AI 仅云版、非结构化 Agent 消费 | [高] |
| **Notion AI** | 全能工作区 | 数据库+Wiki+AI Agent | Business $20/人/月起 | 灵活、AI Agent 强 | 规模化性能差、AI 门槛高 | [高] |
| **Glean** | 企业搜索 | 100+ 应用索引、权限感知搜索 | 企业定制定价 | 跨应用搜索最强、代码智能 | 贵、偏检索非知识构建 | [高] |
| **Guru** | 验证式 KM | 人工审核知识、MCP 交付给 AI | 企业定制 | 准确性高、MCP 集成 | 定价不透明、偏内部政策 | [中] |
| **GitBook** | 技术文档 | Git 同步、MCP Server、AI 助手 | Premium $65/站+$12/人 | 开发者友好、LLM 可发现 | 双计费、偏对外文档 | [高] |
| **Mintlify** | AI 原生文档 | MCP、LLMs.txt、自更新文档 | Pro ~$250/月起 | AI 原生、Cursor 等在用 | 跳价大、非通用 Wiki | [中] |
| **Slab** | 轻量 Wiki | 嵌套页面、统一搜索 | Startup $6.67/人/月 | 最便宜、UI 简洁 | **无 AI 能力** | [高] |

## 3. 代码知识库工具对比

| 工具 | 能力 | 与 sys_kl 关系 | 局限 | 置信度 |
|---|---|---|---|---|
| **Sourcegraph Cody** | 全仓代码索引、跨仓库问答、IDE 集成 | 接近 sys_kl 消费端 | 不管理业务知识、需自建标注层 | [高] |
| **GitHub Copilot Workspace** | 代码库上下文、Issue→PR 工作流 | 代码侧上下文注入 | 无 biz_kl、企业私有部署有限 | [高] |
| **Bloop** | 本地/私有代码语义搜索 | 轻量 sys_kl 检索 | 项目活跃度下降、无协作审核 | [中] |
| **Cursor / Windsurf** | IDE 内 Agent + 代码库索引 | 直接消费知识包的理想终端 | 依赖外部知识源，非 KM 平台 | [高] |

**启示：** sys_kl 应与 IDE Agent 消费协议对齐（JSON 知识包、MCP、RAG 切片），而非重复造代码搜索引擎。

## 4. DDD 知识建模实践

| 实践 | 说明 | 来源置信度 |
|---|---|---|
| **Bounded Context 作为知识边界** | MVP 限定单 BC，biz_kl 条目与 sys_kl 模块均挂在 BC 下 | [高] |
| **上下文映射表** | 业务概念 ↔ 代码模块的显式映射，是知识包核心结构 | [高] |
| **分层归档 sys_kl** | 领域层/应用层/基础设施层分别挂载，便于变更影响分析 | [中] |
| **事件风暴产出 biz_kl** | 领域事件、聚合根可作为 biz_kl 条目模板 | [中] |

---

## 5. AI 编程上下文注入最佳实践

1. **结构化优于全文塞入**：知识包应含条目 ID、类型、关联、摘要，而非原始 PDF/全仓代码。
2. **双层上下文**：业务规则（biz_kl）+ 实现锚点（sys_kl 代码路径/调用链）分开注入，Agent 按需组装。
3. **MCP / API 只读拉取**：GitBook、Guru、Glean 均已走向 MCP；本平台 MVP 应对齐此协议。
4. **人工审核门控**：专家发布后才进入 Agent 可消费集合，避免草稿污染编码建议。
5. **版本与血缘**：变更场景需追溯「哪条 biz_kl 驱动了哪次代码修改」。

---

## 6. 用户痛点（与本产品相关）

1. **上下文碎片化**：文档在 Confluence、逻辑在工程师脑中、代码在 Git，Agent 三者皆缺。
2. **业务-系统断层**：PRD 与实现模块无稳定映射，百万行存量系统尤甚。
3. **知识维护成本高**：全自动逆向不现实，半自动+专家标注是可行路径。
4. **工具各管一段**：KM 平台不管代码，代码工具不管业务，缺少统一「知识包」出口。

---

## 7. 差异化分析

| 维度 | 通用 KM | 代码智能 | **本产品（KL Management）** |
|---|---|---|---|
| biz_kl | 部分（非结构化文档） | 无 | **核心，结构化条目+审核** |
| sys_kl | 无 | 索引/问答 | **DDD 分层+专家标注+半自动** |
| 互链 | 弱 | 无 | **biz ↔ sys 显式映射** |
| Agent 消费 | MCP 起步 | IDE 内置 | **知识包 API/导出（只读）** |
| 治理 | 权限+版本 | 无 | **草稿/发布+血缘+审计** |

**定位陈述：** 面向企业 AI 编程的「业务-系统双库知识平台」，以结构化知识包对接 Agent/IDE，而非再造一个 Confluence 或 Sourcegraph。

---

## 8. 对本项目 MVP 的启示

- 竞品验证：GitBook/Mintlify 的 MCP 与 Glean/Guru 的治理模式值得借鉴
- 不做：全仓自动静态分析、完整 IDE 插件市场
- 必做：单 BC 试点、biz_kl/sys_kl 各 ≥20 条、互链、知识包 JSON 导出
- 成功标准对齐简报：给定真实维护场景，Agent 仅凭平台知识产出方案草稿（人工验收 ≥70%）

# 方案论证：产品知识平台（KL Management）

## 问题陈述

供应链 IT 团队在百万行级存量系统上做功能维护与演进时，业务知识分散在历史文档、PRD、运维记录中，系统逻辑知识隐藏在代码里，依赖老员工口口相传。AI 编程场景下，Agent 缺乏结构化的「懂业务 + 懂系统」上下文，导致方案草稿质量不稳定、新人上手成本高、变更影响分析困难。

核心矛盾：**知识存在但不可消费**——文档有但难检索，代码有但难理解，专家有但难复制。

## 方案选项对比

### **A.** 自研轻量知识平台（推荐）

在现有 Git + 文档系统之上，构建 biz_kl/sys_kl 双库结构化的知识管理平台，提供知识包导出/API 供 Agent 消费。

| 维度 | 评估 |
|------|------|
| 差异化 | biz_kl/sys_kl 分离 + 知识包导出是独特定位，市面无直接竞品 |
| MVP 成本 | 中：需开发核心数据模型、协作流程、API 导出，约 2-4 周 |
| 控制权 | 完全自主，可按 DDD 语义定制 |
| 风险 | 需要领域专家持续投入标注；知识冷启动是最大挑战 |
| 长期价值 | 形成企业级知识资产，可复用到多个 BC/产品线 |

### **B.** 基于现有 KM 平台扩展（Confluence/Notion + AI）

使用 Confluence Rovo 或 Notion AI 等成熟平台，通过标签/空间区分 biz_kl/sys_kl，利用其 AI 能力做知识检索。

| 维度 | 评估 |
|------|------|
| 差异化 | 低：通用 KM 平台，无 biz_kl/sys_kl 语义分离概念 |
| MVP 成本 | 低：配置现有平台，1-2 周即可启动 |
| 控制权 | 受限于平台能力，无法自定义知识包结构 |
| 风险 | 无法保证 biz_kl/sys_kl 严格分离；Agent 消费接口不可控 |
| 长期价值 | 平台锁定，难以沉淀差异化知识资产 |

### **C.** 开源框架二次开发（Doccano + LangChain + Tree-sitter）

使用开源标注工具 + RAG 框架 + 代码分析工具拼装，快速搭建 MVP。

| 维度 | 评估 |
|------|------|
| 差异化 | 中：可定制但需大量集成工作 |
| MVP 成本 | 中高：集成多个组件，调试成本高，约 3-5 周 |
| 控制权 | 开源可修改，但组件兼容性风险大 |
| 风险 | 多组件集成复杂度高；LangChain 生态迭代快，维护成本不确定 |
| 长期价值 | 技术栈开放，但集成债务可能累积 |

### **D.** 纯文档即代码（Docs-as-Code）+ MCP Server

用 Markdown 文件管理知识，通过 Git 版本控制，提供 MCP Server 让 Agent 直接 discover 知识。

| 维度 | 评估 |
|------|------|
| 差异化 | 中高：类似 GitBook/Mintlify 的 MCP 方案，但缺少 biz_kl/sys_kl 语义层 |
| MVP 成本 | 低中：Markdown + Git + MCP Server，约 1-2 周 |
| 控制权 | 高：文件即数据，完全可控 |
| 风险 | 缺乏结构化协作流程（审核、权限、血缘）；纯文本难以表达复杂关系 |
| 长期价值 | 轻量灵活，但随规模增长可能遇到管理瓶颈 |

### **E.** 采购企业知识管理平台（Glean/Guru）

直接采购 Glean 或 Guru 等企业级知识管理平台，利用其 AI Agent 知识交付能力。

| 维度 | 评估 |
|------|------|
| 差异化 | 低：通用企业搜索，无 biz_kl/sys_kl 概念 |
| MVP 成本 | 低：采购 + 配置，但价格高（企业级定制报价） |
| 控制权 | 低：SaaS 黑盒，无法自定义数据模型 |
| 风险 | 采购周期长；数据出境/合规风险；无法适配 DDD 分层需求 |
| 长期价值 | 平台能力强但不可控，难以形成企业专属知识资产 |

### **F.** AI 编程助手内置知识（Cursor/Copilot + Context Files）

利用 Cursor rules、Copilot context 等 AI 编程工具内置的知识管理能力，直接在工作流中维护上下文。

| 维度 | 评估 |
|------|------|
| 差异化 | 低：开发工具附带的轻量能力，非独立知识平台 |
| MVP 成本 | 极低：配置现有工具，数天即可 |
| 控制权 | 低：受限于编辑器生态 |
| 风险 | 知识无法跨工具共享；无协作/审核/版本治理能力；规模受限 |
| 长期价值 | 适合个人场景，不适合团队级知识资产沉淀 |

### **G.** LLM 原生知识图谱（Graph RAG + 自动抽取）

用 LLM 自动从文档和代码中抽取实体/关系，构建知识图谱，提供图谱查询 API。

| 维度 | 评估 |
|------|------|
| 差异化 | 高：技术前沿，自动抽取能力强 |
| MVP 成本 | 高：需要图谱存储、抽取 pipeline、质量校验，约 4-6 周 |
| 控制权 | 中：技术栈开放，但 LLM 抽取质量不可控 |
| 风险 | 自动抽取准确率低（尤其百万行代码）；幻觉问题；与简报「不追求全自动」矛盾 |
| 长期价值 | 技术方向正确，但 MVP 阶段过重 |

## 推荐方案：A（自研轻量知识平台）

### 推荐理由

1. **独特定位无直接竞品**：竞品分析显示，最接近的 GitBook/Mintlify 提供 MCP Server 但无 biz_kl/sys_kl 语义分离；Glean/Guru 提供 Agent 知识交付但为通用搜索。biz_kl + sys_kl 双库互链是差异化核心。
2. **完全符合简报约束**：DDD 分层、知识包导出、半自动 sys_kl、只读 API——所有约束均可自主实现。
3. **MVP 范围可控**：聚焦单个 BC、20+ 条目、知识包导出，2-4 周可验证核心价值。
4. **知识资产自主可控**：形成企业级结构化知识资产，可复用到多个产品线。

### SWOT 分析

| | 内部 | 外部 |
|---|---|---|
| **优势 (S)** | 完全自主控制数据模型与 API；DDD 语义天然匹配 biz_kl/sys_kl 分离；知识包导出直接对接 Agent 消费场景 | biz_kl/sys_kl 分离是市场空白，无直接竞品 |
| **劣势 (W)** | 需要从零开发核心功能；冷启动依赖专家标注投入；团队无现成知识平台开发经验 | 竞品（GitBook/Mintlify）的 MCP 方案已验证 LLM discoverability 需求 |
| **机会 (O)** | 可复用到多条产品线；积累标注数据后反哺自动化引擎；形成企业知识壁垒 | AI 编程场景爆发，结构化知识需求增长 |
| **威胁 (T)** | 领域专家时间投入不足导致知识质量差；Agent 消费端未就绪导致验收失败 | 大厂可能推出类似产品（如 Notion 增加 DDD 语义层） |

### ADR-004: MVP 技术栈选择——轻量 Web 应用（FastAPI + SQLite + 静态前端）

**状态**: Proposed  
**决策日期**: 2026-06-07  
**决策者**: pm-analyst

#### 背景

MVP 需要快速验证 biz_kl/sys_kl 双库 + 知识包导出的核心价值，技术栈需满足：开发速度快、部署简单、后续可迁移。

#### 决策

- 后端：Python FastAPI（RESTful API，原生异步，类型安全）
- 存储：SQLite（单文件数据库，MVP 足够，后续可迁移 PostgreSQL）
- 前端：静态 HTML + HTMX（无需构建工具，服务端渲染）
- 部署：单机 Python 进程，无容器依赖

#### 理由

- 团队有 Python 经验，FastAPI 学习成本低
- SQLite 零配置，适合单 BC 试点（数据量 ≤1000 条目）
- 静态前端 + HTMX 避免前端工程化开销
- 技术栈轻量，验证失败时沉没成本低

#### 后果

- ✅ 2-4 周可完成 MVP 开发
- ✅ 部署极简，一台机器即可运行
- ⚠️ SQLite 不支持高并发，但 MVP 阶段用户 ≤10 人
- ⚠️ 后续扩展需迁移数据库，但数据结构设计时可预留兼容性

### ADR-005: 知识包导出格式——JSON Schema + Markdown 双格式

**状态**: Proposed  
**决策日期**: 2026-06-07  
**决策者**: pm-analyst

#### 背景

MVP 需要提供「给 Agent 用的知识包」，消费端可能是 API 调用也可能是离线文件。

#### 决策

- JSON 格式：结构化数据，包含 biz_kl 条目、sys_kl 条目、互链关系、血缘信息，符合预定义 JSON Schema
- Markdown 格式：人类可读版本，按业务概念分组，每条包含概念描述、关联代码模块、变更历史

#### 理由

- JSON 适合 Agent/API 消费，可被程序解析
- Markdown 适合人工审阅和 Git 版本控制
- 双格式覆盖 MVP 两种消费场景（API 拉取 + 文件导出）

#### 后果

- ✅ 同时满足机器和人类消费
- ⚠️ 需维护两种格式的一致性（可由同一数据源生成）
- ⚠️ JSON Schema 需要版本管理，向后兼容

# Proposal: 产品知识平台 MVP — biz_kl/sys_kl 双库知识管理

## Why

供应链 IT 团队在百万行级存量系统上做功能维护与演进时，业务知识（设计文档、PRD、运维记录）与系统逻辑知识（代码结构、调用链、模块职责）分散在不同系统中，依赖老员工口口相传。AI 编程场景下，Agent 缺乏结构化的「懂业务 + 懂系统」上下文，导致方案草稿质量不稳定、新人上手成本高。

竞品分析（Confluence Rovo、Notion AI、Glean、Guru、GitBook、Mintlify、Slab）显示：市面上无产品同时提供 biz_kl/sys_kl 语义分离 + 知识包导出供 Agent 消费的能力。这是我们的差异化机会。

## What changes

### 新增能力

1. **biz_kl 知识库**：支持文档导入、结构化条目管理（概念/流程/规则）、草稿-审核-发布流程
2. **sys_kl 知识库**：支持按 DDD 分层手动/半自动挂载代码路径、专家注释、与 biz_kl 互链
3. **知识包导出**：提供 JSON + Markdown 双格式导出，供 Agent/IDE 消费
4. **基础协作**：3 角色（领域专家、开发者、管理员）权限与审计日志
5. **血缘追踪**：记录条目来源、创建/修改者、关联原始文档或代码片段

### MVP 范围限定

- 单个 bounded context（供应链 IT 试点子系统）
- biz_kl ≥20 条、sys_kl ≥20 条可发布条目
- 只读 API/导出，不开放写入
- 半自动 sys_kl 标注（不追求全自动逆向）

### 不做

- 全仓自动静态分析引擎
- IDE 插件
- 多租户 SaaS 计费
- 通用企业搜索/RAG

## Impact

### 用户影响

| 角色 | 变化 |
|------|------|
| 领域专家 | 从口述/散落文档 → 结构化 biz_kl 条目贡献与审核 |
| 开发者 | 从人工查找文档/代码 → API/导出获取结构化知识包 |
| 管理员 | 从手动协调 → 权限、版本、质量的平台化治理 |

### 技术影响

- 新增 FastAPI 后端 + SQLite 存储
- 新增知识包 JSON Schema 定义
- 新增 biz_kl ↔ sys_kl 互链关系模型
- 不影响现有 Git 工作流和文档系统

### 业务影响

- 验证「结构化知识 → Agent 方案质量提升」的因果链
- 形成可复用到多条产品线的知识资产模板
- 降低新人上手成本（从口口相传 → 自助查询）

## Acceptance scenarios

| # | 场景 | 验收标准 |
|---|------|---------|
| AC1 | 领域专家创建并发布一条 biz_kl 条目（业务概念） | 条目包含名称、描述、关联流程/规则、审核状态 |
| AC2 | 开发者创建并发布一条 sys_kl 条目（代码模块） | 条目包含模块路径、DDD 层级、关联 biz_kl 条目 |
